=== Завершение работы над API дескрипторов процессов 2

Контактное лицо: Konstantin Belousov <kib@FreeBSD.org>

Ссылки: +
link:https://reviews.freebsd.org/D57124[sys: добавление pdopenpid(2)] URL: link:https://reviews.freebsd.org/D57124[] +
link https://reviews.freebsd.org/D57163[pddupfd(2)] https://reviews.freebsd.org/D57163[]

После добавления системных вызовов man:pdwait[2] и man:pdrfork[2] я обратил внимание на другие недостающие возможности, которые запрашивают прикладные программисты.
Самым крупным запросом, по-видимому, является возможность получения дескриптора процесса для существующего процесса.

В настоящее время только один файловый дескриптор может ссылаться на внутреннюю структуру struct procdesc в ядре, что отчасти объясняет, почему интерфейс для открытия процесса по pid ещё не реализован.
В ходе работы была добавлена возможность для procdescs иметь более одного файла, указывающего на них.
Атрибуты, управляющие поведением procdesc, например, daemon (закрытие файла не завершает процесс), были перенесены из procdesc в файл.

Это изменение позволило расширить внутренние интерфейсы procdesc для реализации системного вызова man:pdopenid(2).

Возможность, реализованная, например, в дескрипторах pidfd в Linux, — это системный вызов pidfd_getfd(), который дублирует указанный файловый дескриптор из целевого процесса в вызывающий процесс.
Реализация этого для FreeBSD, названная man:pddupfd(2), относительно проста после получения вспомогательной функции fget_remote(9).

Проблема возникла, когда был разработан алгоритм проверки привилегий, необходимых для выполнения операции.
Ядро проверяет результат p_candebug(), чтобы определить, разрешено ли что-либо, что напрямую обращается к программным ресурсам удалённого процесса.
Но результат p_candebug() действителен только пока удерживается блокировка целевого процесса.
Кроме того, p_candebug() запрещает действия, если целевой процесс изменяет выполняемую программу с помощью man:execve(2), что может изменить привилегии процесса, если образ имеет set-uid или set-gid.
В целом, простая проверка с помощью p_candebug() неадекватна, потому что мы не можем удерживать блокировку процесса на протяжении всего fget_remote().

Для этого был разработан механизм, обеспечивающий взаимное исключение между выполнением exec в целевом процессе и вызывающим процессом, названный execblock.
Также были добавлены вспомогательные функции для получения ссылки на текущее vmspace процесса, чтобы избежать использования execblock, когда для действия требуется только согласованное адресное пространство цели, например, чтение строк процесса или копирование памяти процесса.
Существующие места в системе, подверженные этой гонке, были идентифицированы, и использование execblock или интерфейсов ссылок на vmspace было применено по мере необходимости.

Затем man:pddupfd(2) был реализован с помощью fget_remote() и execblock.
