[[_procdesc_debugging_api]]
=== Procdesc: API отладки

Контакт: Konstantin Belousov <kib@FreeBSD.org>

Проект по расширению API дескрипторов процессов продолжался с целью обеспечить полный контроль над процессом с помощью дескрипторов, в частности отладку.
Я хотел сделать возможным отказаться от ссылок на pid как идентификаторы процессов.
Вехой для этого должна стать демонстрация включения режима capsicum для некоторого нетривиального отладчика; я выбрал man:truss[1], поскольку после подключения к целевой программе ему не требуется доступ ни к файловой системе, ни к сетевому пространству имён.

Полуочевидное решение здесь — ввести man:pdptrace[2], который эквивалентен man:ptrace[2], но принимает дескриптор процесса в качестве обозначения процесса.
Нам нужно уметь получать уведомления о событиях отладки процесса, которые предоставляются семейством системных вызовов waitpid[2] для управления по pid.
И нам нужен способ получать дескриптор процесса для нового потомка, ответвлённого от отлаживаемой программы, чтобы продолжать трассировку всех потомков.

Ранее был добавлен системный вызов man:pdopenpid[2], который позволяет получить дескриптор произвольного процесса.
Существующие операции над дескрипторами процессов несколько ограничены: владелец дескриптора может ожидать уведомление о завершении с помощью man:kqueue[2] и при некоторой удаче получить статус завершения процесса.

Последний пункт требует некоторых пояснений.
Поскольку вызов man:pdwait[2] был добавлен недавно, в ядре было некоторое количество обходных решений, позволявших вызовы man:waitpid[2] для pid процессов, созданных с помощью man:pdfork[2].
В результате вызывающий man:waitpid[2] мог забрать процесс раньше, чем владелец дескриптора процесса смог вызвать man:pdwait[2].
Аналогично, если на один и тот же процесс открыто более одного дескриптора процесса, только первый вызывающий man:pdwait[2] мог получить статус завершения с помощью man:pdwait[2], делая остальные дескрипторы бесполезными.

Перечисленный набор проблем также делал очень трудным корректное использование предложенного man:pdptrace[2].
Отлаживаемый процесс мог перехватывать события у дескрипторов процессов, и наоборот.
Простое запрещение man:wait[2] для процессов с открытыми дескрипторами не является вариантом по двум причинам:
* обратная совместимость: man:waitpid[2] уже был разрешён, и существующие бинарные файлы полагались на него
* если отлаживаемая программа использовала man:fork[2] для создания потомка, она ожидает получить уведомление о завершении (например, SIGCHLD) и статус завершения от man:wait[2]

Решение было многосторонним.
Во-первых, мы должны отложить сбор (reaping), если есть открытые дескрипторы процессов, или, если процесс был создан с помощью man:fork[2], мы не должны собирать его до тех пор, пока родитель не вызовет man:wait[2] по pid.
Во-вторых, статус завершения нужно сохранять в приватных данных дескрипторов процесса даже после сбора, чтобы позволить man:pdwait[2] по любому из дескрипторов.
Это было реализовано путём предоставления битовой карты «ссылок зомби» в структуре ядра struct proc.
Каждая ссылка зомби предотвращает сбор и очищается соответствующим вызовом man:waitpid[2] или man:pdwait[2].
Только когда все зарегистрированные ссылки очищены, зомби может быть собран.
Если процесс создан с помощью man:pdfork[2] или открыт с помощью pdopenpid[2], он получает ссылку зомби procdesc.
Если процесс был создан с помощью man:fork[2], он получает ссылку зомби «родитель».
По умолчанию pdfork[2] также устанавливает родительскую ссылку, чтобы разрешить man:waitpid[2] для совместимости.
Новый флаг man:pdfork[2] PD_NOWAITPID предотвращает это.

Затем события, подобные wait, должны работать с дескрипторами процессов.
Фильтр событий man:kqueue[2] для procdesc был расширен подсказками NOTE_PDSIGCHLD, чтобы сообщать, что man:pdwait[2] может получить событие трассировки или завершения по дескриптору.

Затем man:pdptrace[2] смог полезно управлять целевой программой.
Новый вызов ptrace для получения списка присоединённых процессов PT_GET_CHILDREN позволил man:pdptrace[2] получать дескрипторы потомков, созданных через fork.

Со всеми реализованными функциями стало возможным преобразовать man:truss[1] так, чтобы он использовал только дескрипторы процессов для управления трассируемыми процессами.
Существующий режим использования pid был сохранён и может быть выбран опцией '-y' как аварийный переключатель, а также для удобного сравнения и отладки нового режима.
