=== Портирование проекта rdma-core во FreeBSD

Инфраструктура Remote Direct Memory Access (RDMA) обеспечивает высокопроизводительное межсоединение между вычислительными узлами и узлами хранения.
Она может работать поверх различных физических сетей, например Ethernet и Infiniband.

Реализация стека RDMA состоит из нескольких компонентов.
Есть ядерная инфраструктура и драйверы для Host Channel Adapters (HCA), обеспечивающие доступ к verbs ядра (прим. переводчика: verbs — стандартный API RDMA/InfiniBand).
Пользовательские приложения никогда не взаимодействуют с устройствами ядра напрямую; основная библиотека libibverbs и зависящие от вендора пользовательские драйверы предоставляют унифицированные и специфичные для устройства verbs.

Поскольку RDMA нацелена на операции с низкой задержкой и малыми накладными расходами, производительные HCA снимают с CPU множество операций.
Кроме того, типичные встроенные операции, такие как отправка и приём, могут инициироваться и завершаться в пользовательском пространстве, где ядро лишь помогает при установлении и разрыве соединения.
Из-за этого пользовательский программный стек RDMA критически важен для её работы.

Базовая система FreeBSD включает порт так называемого ядерного компонента OFED, ядерные драйверы, а также пользовательское ядро (libibverbs) и пользовательские драйверы, например libmlx5 для управления HCA Nvidia Connect-X4 и более поздними.
Со временем ядерные части получают значительные обновления из кода infiniband в ядре Linux, который становится домом для обновлённого OFED.
Пользовательская часть OFED была преобразована в пользовательский проект rdma-core, который поддерживает только Linux (и glibc).
Поскольку пользовательские драйверы в rdma-core обеспечивают существенную функциональность, а пользовательские компоненты RDMA во FreeBSD довольно устарели, ситуация в целом требует решения.

Мы попытались обновить внутрисистемные пользовательские компоненты, импортировав серию коммитов rdma-core с зависимостями, но быстро выяснилось, что это нецелесообразно.
Вместо этого мы начали изучать, что потребуется, чтобы заставить rdma-core компилироваться и работать во FreeBSD.

Во-первых, был ряд отсутствующих специфичных для glibc API, которые использовались в rdma-core, например strdupa() и подобные, main:tdestroy(3), некоторые функции pthread.
Их было легко обработать в базовой системе, и их добавление пошло на пользу всей истории портирования FreeBSD.

Далее, и более серьёзно, непортируемые особенности glibc использовались повсюду в исходниках, и попытка охватить их все вызвала бы огромный патч портирования, который проблематично отправить в upstream, даже для сотрудничающего upstream.
Вместо этого была сформирована и разработана идея использования подхода, аналогичного LinuxKPI для кода ядра, названного LinuxAPI.
В отличие от LinuxKPI, который обрабатывает архитектурные несоответствия между ядром Linux и ядром FreeBSD в дополнение к различным C-интерфейсам, LinuxAPI должен сглаживать различия вокруг расширений одной и той же базовой функциональности, определённой POSIX.
Речь в основном идёт о частях, которые не определены POSIX, но необходимы для работы RDMA, таких как перечисление сетевых интерфейсов или обнаружение устройств с поддержкой rdma и их возможностей и т. д.

Похоже, люди уже считают LinuxAPI полезным за пределами усилий по портированию rdma-core; есть проект github.com/freebsd/linuxapi, который берёт разработанный набор заголовков и расширяет его дальше.
В настоящее время мы работаем над предоставлением разрешительной лицензии, чтобы сделать библиотеку полезной без дополнительных условий.

Наша первоначальная цель, также ограниченная доступным оборудованием, — заставить rdma-core работать с картами ConnectX-4.
Разумеется, мы приветствуем всех вендоров, заинтересованных в RDMA во FreeBSD, улучшать порт для надлежащей поддержки их карт.

Результат портирования доступен в виде репозитория.
Мы также стараемся отправить изменения в upstream, чтобы FreeBSD стала второй нативно поддерживаемой платформой для rdma-core.
Pull Request в проект на github отправлен.
В настоящее время идёт блокирующее обсуждение о способе организации CI для платформы FreeBSD.
Глеб Попов создал порт package:net/rdma-core[] из ответвлённых исходников, который уже находится в дереве портов.

Изменения ядра, необходимые для работы порта, были на удивление небольшими и локализованными.
Они в основном состояли из исправлений ошибок в путях кода, ранее не задействованных пользовательским пространством, поскольку пользовательского пространства не было.
Самая интересная часть — пожалуй, разница в поведении man:ioctl[2] между Linux и FreeBSD, где Linux может одновременно вернуть ошибку и выполнить copyout структуры данных.
Эта проблема уже наблюдалась в LinuxKPI, и работа по портированию предоставила там общее решение.

Спонсор: Nvidia networking
