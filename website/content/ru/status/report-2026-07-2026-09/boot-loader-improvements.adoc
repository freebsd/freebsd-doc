Контакт: Warner Losh <imp@FreeBSD.org>

Работа в этом квартале расширила поддержку загрузчиком сжатых образов, дисков памяти и сетевой загрузки по HTTP, с вниманием как к интеграции с iPXE, так и к полноте man:loader.efi[8].
Она также представила тестовый фреймворк на основе QEMU, охватывающий многие варианты загрузки FreeBSD.

Загрузчик теперь может читать файлы, сжатые с помощью XZ или Zstandard, так же, как он уже обрабатывал файлы gzip и bzip2.
Поддержка XZ включена по умолчанию в загрузчиках BIOS и EFI, включая поддержку сжатых образов дисков памяти, таких как установочные образы FreeBSD.
Поддержка Zstandard доступна как опция сборки.

Обработка дисков памяти была обобщена, чтобы загрузчик мог динамически создавать устройство `md`.
Это обеспечивает запасной вариант на системах, чья прошивка UEFI не реализует протокол RamDisk, — ситуация, встречающаяся на некоторых малых и встраиваемых системах.
Полученный диск памяти экспортируется в ядро и может содержать как ядро, так и корневую файловую систему.
Загруженные образы дисков памяти теперь используют правильный тип памяти UEFI, а загрузку можно прервать клавишей Escape.
Это заменяет необходимость использования сторонней надстройки [.filename]#memdisk_uefi.efi#, которая требовалась людям ранее для интеграции с iPXE.
Теперь [.filename]#loader.efi# также может загружать образы через службы загрузки iPXE, требуя только базовые сетевые модули DXE в образе прошивки UEFI.

Поддержка EFI HTTP ранее зависела от того, что прошивка загрузила [.filename]#loader.efi# через UEFI HTTP Boot, и была ограничена сервером, выбранным прошивкой.
Теперь загрузчик принимает произвольные спецификации устройств `http[N]://host[:port]/path`.
Их можно использовать как `rootdev`, в [.filename]#loader.conf# или интерактивно, независимо от того, как был запущен сам загрузчик.
Реализация может либо повторно использовать существующую сетевую конфигурацию загрузчика, либо попросить сетевой стек прошивки выполнить DHCP.

Клиент DHCP теперь запрашивает опцию производителя FreeBSD, содержащую URL начального образа диска памяти.
С этой опцией машина может запустить [.filename]#loader.efi# напрямую по сети, обнаружить отсоединённый корневой образ через DHCP, получить этот образ по HTTP и загрузиться с него.
Была проявлена осторожность при передаче владения сетевым интерфейсом между собственным сетевым стеком загрузчика и стеком UEFI HTTP.
Это необходимо, поскольку каждому стеку требуется различный доступ к сетевым протоколам прошивки.

Новый фреймворк [.filename]#tools/boot/boot-test.sh# использует QEMU для тестирования загрузки на aarch64, amd64, armv7, powerpc64, powerpc64le и riscv64.
Он задействует применимые окружения BIOS, UEFI, OpenFirmware и PReP с конфигурациями CD, MBR, GPT, сети и дисков памяти, а также загрузчики Lua, Forth и simple.
Тесты сетевой загрузки по HTTP и цепной загрузки [.filename]#gptboot.efi# были добавлены позже в квартале.
Фреймворк пока не является установленным тестом, поскольку он собирает и тестирует несколько целевых архитектур с одного хоста.

Тесты цепной загрузки сопровождали исправление для систем, использующих [.filename]#gptboot.efi# для выбора между системными разделами A/B.
После цепной загрузки [.filename]#loader.efi# мог пропустить выбранный раздел и вместо этого загрузить другой системный раздел.
Теперь выбранный раздел пробуется первым, а обычный поиск родственных разделов остаётся как запасной вариант.
Отдельное изменение загрузчика, которое мешало некоторым конфигурациям цепной загрузки ZFS, было отменено.

Другая работа добавила страницу руководства man:loader.kboot[8], параметры сборки для исключения загрузчиков x86 BIOS и userboot из систем только с UEFI, а также защитные проверки для прошивок, которые объявляют непригодные протоколы графического вывода.
